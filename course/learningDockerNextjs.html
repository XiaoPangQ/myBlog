Docker 部署 Next.js + Prisma + PostgreSQL 实战指南

从零把一个 Next.js 全栈项目容器化并部署到服务器：编写 Dockerfile 多阶段构建、Compose 编排应用与数据库、镜像仓库推送拉取、 数据库迁移、发版更新，每一步都附常见报错与解决方法。

11 个章节 30+ 常见问题 含私有镜像仓实战流程 以 Next.js 14/15 为准

01 部署前必读：整体架构

这套技术栈各管什么

组件 角色 跑在哪
Next.js Web 框架：页面 + API 路由 容器 A（监听 3000 端口）
Prisma ORM：代码里操作数据库的类型安全工具 打包进容器 A（编译期生成客户端）
PostgreSQL 数据库：真正存数据的地方 容器 B（监听 5432 端口）
📌 关键认知：Prisma 不是一个"服务"
Prisma 只是代码依赖（node_modules 里的一个包），构建时执行 prisma generate 生成数据库客户端，运行时随 Next.js 一起跑。不需要也不应该单独为 Prisma 建容器——需要单独照顾的只有 PostgreSQL。

整体部署路线图

        │
        ▼

        │
        ▼

        │                                  ┌─────────────────────────┐

两种部署形态，先选定你的路线

形态 说明 适合
单镜像 + Compose（本指南主线） Next.js 打一个镜像；PostgreSQL 用官方镜像；compose 文件编排两者 绝大多数项目，推荐
纯 docker run 两条 docker run 手动起两个容器，用 --link / 同网络通信 临时验证、理解原理
⚠️ 最大的坑：开发时 localhost，容器里不能用
开发时 DATABASE_URL=postgresql://...@localhost:5432/db 能跑，是因为数据库跑在你本机。容器化后 app 是独立容器，localhost 指的是它自己容器内部——必须改成 compose 里的服务名（如 db）。这是本技术栈第一高频报错，先记住，后面第 10 章还会见到它。

02 项目准备与环境变量

Step 1：开启 standalone 输出模式（必做）

standalone 让 Next.js 构建产物只包含运行必需的文件，镜像体积从 1GB+ 瘦身到 200MB 左右。改一行配置： 

// next.config.js（或 next.config.mjs / .ts）
const nextConfig = {
  output: 'standalone',   // <-- 加这一行
};

module.exports = nextConfig;

加完后本地跑一次 npm run build，确认出现 .next/standalone/ 目录，说明生效。

Step 2：规划环境变量（三份文件）

文件 用途 提交到 Git？
.env 本地开发，Prisma CLI 读它 ❌ 不提交
.env.production 构建时需要的前端变量（NEXT_PUBLIC_ 开头的会打进前端包） 按团队约定
.env.docker 容器运行时注入（数据库地址等），本指南用 compose 注入 ❌ 不提交
🚫 安全红线：密码不进镜像、不进 Git
数据库密码、镜像仓账号等敏感信息只放在服务器上的 .env 或 compose 环境变量里，绝不写进 Dockerfile（写进去就永久烙在镜像层里，谁都扒得出来）、不提交 Git。镜像仓的登录凭证也一样——docker login 输入即可，别存笔记里发到任何公开处。

Step 3：确认 Prisma Schema 就绪

// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")   // 从环境变量读，容器部署的关键
}

Step 4：创建 .dockerignore（不做镜像会巨大 + 缓存失效）

在项目根目录新建 .dockerignore：

node_modules
.next
.git
.gitignore
*.md
.env
.env.*
!.env.production
npm-debug.log*
Dockerfile
docker-compose*.yml
.dockerignore

两个目的：① node_modules 不进构建上下文（传给 Docker 的体积小、构建快）；② .env 不被意外打进镜像。

03 编写 Dockerfile（多阶段构建）

为什么必须多阶段

Next.js + Prisma 构建需要完整的 devDependencies（prisma CLI、TypeScript 等），但运行时不需要。单阶段构建会把编译工具全打进镜像——1GB 起步还留安全隐患。多阶段构建 = 编译车间和成品仓库分开。

完整 Dockerfile（可直接抄）

项目根目录新建 Dockerfile：

# ============ 阶段 1：deps 安装依赖 ============
FROM node:20-alpine AS deps
WORKDIR /app

# 先复制清单再安装 —— 依赖不变时命中 Docker 缓存，秒级完成
COPY package.json package-lock.json ./
RUN npm ci

# ============ 阶段 2：builder 构建 ============
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .

# 构建期需要 DATABASE_URL（prisma validate / 页面里若直连数据库）
# 给个占位值即可，运行时会用真实值覆盖
ENV DATABASE_URL="postgresql://placeholder:placeholder@localhost:5432/placeholder"

RUN npx prisma generate && npm run build

# ============ 阶段 3：runner 运行 ============
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

# Prisma 在 alpine 上需要 openssl（Debian 基础镜像自带，alpine 必须显式装）
RUN apk add --no-cache openssl

# 非 root 用户跑应用，安全性更好
RUN addgroup --system --gid 1001 nodejs \
 && adduser --system --uid 1001 nextjs

# standalone 产物 + prisma 必需文件
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/prisma ./prisma
COPY --from=builder --chown=nextjs:nodejs /app/node_modules/.prisma ./node_modules/.prisma
COPY --from=builder --chown=nextjs:nodejs /app/node_modules/@prisma ./node_modules/@prisma

USER nextjs
EXPOSE 3000
ENV PORT=3000 HOSTNAME="0.0.0.0"

# 启动：先执行数据库迁移，再起服务
CMD ["sh", "-c", "npx prisma migrate deploy && node server.js"]

这个 Dockerfile 的 6 个关键点

写法 为什么
先 COPY package.json 再装依赖 改业务代码不重装依赖，构建从分钟级降到秒级（缓存命中）
npx prisma generate 在 builder 阶段 生成 Prisma Client 供构建使用；产物复制到 runner
apk add openssl alpine 上没有 openssl 时 Prisma 启动直接报 Query engine error
复制 node_modules/.prisma 和 @prisma standalone 模式不会自动带上 Prisma 客户端，漏了必报 @prisma/client did not initialize
HOSTNAME="0.0.0.0" 不设的话容器外访问不到服务（只监听容器内部回环）
CMD 里先 migrate deploy 容器每次启动自动把数据库结构升到最新——发版不用手动改库
💡 偷懒选择：node:20（Debian 版）
用 FROM node:20（Debian 基础）可以省掉 apk add openssl、bcrypt/sharp 等原生模块的兼容烦恼，代价是镜像大 300MB 左右。第一次部署求稳可以用它，跑通了再换 alpine 瘦身。

04 Docker Compose 编排（app + db）

完整 docker-compose.yml

项目根目录新建 docker-compose.yml：

services:
  # ---------- 数据库 ----------
  db:
    image: postgres:16-alpine
    container_name: app-db
    restart: always
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: "改成一个强密码"       # 生产建议从 .env 注入
      POSTGRES_DB: appdb
    ports:
      - "5432:5432"       # 生产环境建议删掉这行，不暴露数据库端口到公网
    volumes:
      - pgdata:/var/lib/postgresql/data   # 数据持久化的关键！
    healthcheck:                          # 让 app 等 db 真正就绪再启动
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 10

  # ---------- Next.js 应用 ----------
  app:
    image: "next-app:1.0.0"        # 本地构建用；服务器上换成仓库地址
    container_name: app-web
    restart: always
    ports:
      - "80:3000"            # 浏览器访问 80 → 容器内 3000
    environment:
      # 注意 host 是 db（服务名），不是 localhost！
      DATABASE_URL: "postgresql://appuser:你的强密码@db:5432/appdb"
    depends_on:
      db:
        condition: service_healthy   # 等 healthcheck 通过才启动，避免连接被拒

volumes:
  pgdata:

四个必懂的配置点

配置 作用 踩坑提醒
volumes: pgdata 数据库文件存在宿主机，容器删了数据还在 没有它，每次发版数据全丢
restart: always 容器崩溃 / 服务器重启后自动拉起 不加的话挂了就没人管
healthcheck + depends_on condition app 等数据库真正能接连接了才启动 Postgres 启动有初始化过程，"容器起了"≠"能连了"
DATABASE_URL 里的 @db compose 内置 DNS，服务名即主机名 写成 localhost 必报 ECONNREFUSED 127.0.0.1:5432

进阶：密码不放 yml 里，用 .env 注入

# 服务器上与 docker-compose.yml 同目录放一个 .env 文件：
POSTGRES_PASSWORD=真实强密码
DATABASE_URL=postgresql://appuser:真实强密码@db:5432/appdb

# compose 里引用（compose 会自动读同目录 .env）：
    environment:
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}"
      DATABASE_URL: "${DATABASE_URL}"

05 本地构建与启动

构建镜像：为什么用 buildx 而不是 build

你在 Windows/Mac（包括 Apple 芯片）上构建的镜像，默认是本机架构（如 arm64）；而大多数服务器是 linux/amd64——架构不匹配的镜像在服务器上根本跑不起来（报 exec format error）。所以始终显式指定平台： 

# -f 指定 Dockerfile 位置；-t 命名；末尾的 . 是构建上下文=当前目录
docker buildx build --platform linux/amd64 -t next-app:1.0.0 --load .

# Dockerfile 不在根目录时（比如放在 docker/prod/ 下）：
docker buildx build --platform linux/amd64 -f docker/prod/Dockerfile -t next-app:1.0.0 --load .

# 验证镜像架构（期望 Architecture: amd64）：
docker inspect next-app:1.0.0 --format "{{.Architecture}}"

# 本地快速验证（compose 起 app+db）：
docker compose up -d
docker compose ps            # 两个容器都应 Up
docker logs -f app-web      # 看 app 日志，确认 migrate deploy 成功 + Ready on port 3000
⚠️ buildx 的 --load 别忘了
老命令 docker build 构建完自动进本地镜像列表；buildx build 默认只构建不加载，本地要使用需加 --load（直接 push 到仓库时则不需要）。

浏览器访问 http://localhost（80 端口映射），页面正常即本地验证通过。

06 推送镜像到仓库

三种仓库怎么选

仓库 地址示例 适合
私有镜像仓（学校/公司 Harbor） harbor.xxx.edu.cn/项目组/app 内网服务器，速度快、可控
Docker Hub 你的用户名/app 公开镜像、个人项目
阿里云 ACR 等 registry.cn-hangzhou.aliyuncs.com/空间/app 国内服务器拉取快

标准推送三步

# 1. 登录（输入账号密码；凭证会存在本机，之后不用重复登录）
docker login harbor.xxx.edu.cn

# 2. 给镜像打上仓库完整地址的 tag（如果构建时 -t 已带完整地址，这步可省）
docker tag next-app:1.0.0 harbor.xxx.edu.cn/myteam/next-app:1.0.0

# 3. 推送
docker push harbor.xxx.edu.cn/myteam/next-app:1.0.0

# 推送时可以同时推多个 tag：latest 方便服务器默认拉，版本号便于回滚
docker tag next-app:1.0.0 harbor.xxx.edu.cn/myteam/next-app:latest
docker push harbor.xxx.edu.cn/myteam/next-app:latest
💡 版本号建议用可追溯的格式
v1.0.0、v1.0.1 这种语义化版本 + Git commit 短哈希（如 v1.0.1-3f2a9c）组合最佳：出了问题能一键回滚到上一个 tag，也能精确对应到那次代码提交。

07 服务器拉取与运行

服务器上的准备（一次性）

  1. 装好 Docker 与 Docker Compose 插件（docker -v、docker compose version 能出版本号即可）
  2. 登录镜像仓库（和本地一样的 login 命令）
  3. 建项目目录：mkdir -p /opt/myapp && cd /opt/myapp
  4. 把 docker-compose.yml 和 .env 放进该目录（scp / 宝塔 / SFTP 均可），并确认防火墙/安全组放行 80 端口

拉取并启动

# 服务器上（compose 里的 image 改成仓库完整地址）：
#   image: "harbor.xxx.edu.cn/myteam/next-app:1.0.0"

docker compose pull          # 拉取 compose 里定义的镜像
docker compose up -d         # 后台启动 app + db
docker compose ps           # 状态都应是 Up (healthy)
docker logs -f app-web      # 实时看应用日志（Ctrl+C 退出查看，不影响容器）

纯 docker run 方式（理解原理 / 快速验证用）

不写 compose 时的等价操作——先建网络再起两个容器：

# 1. 建一个专用网络，让两个容器能互相用名字访问
docker network create appnet

# 2. 起 PostgreSQL（带数据卷持久化）
docker run -d --name app-db --network appnet \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD="你的强密码" \
  -e POSTGRES_DB=appdb \
  -v pgdata:/var/lib/postgresql/data \
  --restart always \
  postgres:16-alpine

# 3. 起 Next.js（DATABASE_URL 的 host 用容器名 app-db）
docker run -d --name app-web --network appnet \
  -p 80:3000 \
  -e DATABASE_URL="postgresql://appuser:你的强密码@app-db:5432/appdb" \
  --restart always \
  harbor.xxx.edu.cn/myteam/next-app:1.0.0

用 run.sh 把命令固化成脚本

每次敲长命令容易错，写成脚本一键执行（服务器上 vi run.sh）： 

#!/bin/bash
# run.sh —— 停旧容器、删旧容器、起新容器
docker stop app-web
docker rm app-web
docker run -p 80:3000 --name app-web \
  --network appnet \
  -e DATABASE_URL="postgresql://appuser:你的强密码@app-db:5432/appdb" \
  -d --restart always \
  harbor.xxx.edu.cn/myteam/next-app:1.0.0

# 保存退出后授权 + 运行：
chmod +x ./run.sh
./run.sh
📌 脚本里的镜像版本每次发版要改
vi run.sh 把 tag 换成新版本号再执行；compose 党则改 docker-compose.yml 里的 image 后 docker compose pull && docker compose up -d，更省事。

08 数据库初始化与迁移

三条 Prisma 命令，别再混了

命令 做什么 什么时候用
prisma migrate dev 生成迁移文件 + 应用到库 + （会重置数据！） 仅本地开发，生产环境禁用
prisma migrate deploy 只应用已提交的迁移文件，不重置数据 生产部署专用（本指南 CMD 里就是它）
prisma db push 直接把 schema 推到库，不生成迁移文件 原型快速验证，正式项目不推荐

本方案的迁移时机：容器启动时自动执行

第 3 章 Dockerfile 的 CMD 已包含 npx prisma migrate deploy，配合数据卷，效果是： 发新版 → 容器重启 → 自动执行新增的迁移文件 → 表结构更新 → 历史数据保留。

手动操作数据库（排查 / 验证用）

# 进入 postgres 容器的交互式终端（psql）
docker exec -it app-db psql -U appuser -d appdb

# 常用 psql 命令：
\dt                          # 列出所有表（确认迁移是否成功）
\d "User"                   # 查看某张表结构
SELECT count(*) FROM "User"; # 数一下数据条数
\q                          # 退出

# 进入 app 容器手动执行迁移（比如排查启动失败）：
docker exec -it app-web npx prisma migrate deploy

# 备份数据库（重要！发大版本前先备份）：
docker exec app-db pg_dump -U appuser appdb > backup_$(date +%F).sql
💡 首次部署 vs 后续发版的区别
首次 up -d：Postgres 容器初始化空库 → migrate deploy 建出所有表。后续发版：数据卷里已有库，migrate deploy 只执行新增的迁移文件。切记发版前 pg_dump 备份一次，给自己留后悔药。

09 发新版完整流程（日常最常用）

代码改完了，从提交到上线完整走一遍：

本地：构建 → 推送

# ① 改好代码，本地验证通过后，构建新版本镜像（版本号 +1）
docker buildx build --platform linux/amd64 \
  -f Dockerfile -t harbor.xxx.edu.cn/myteam/next-app:v1.0.1 --push .

# （--push 直接构建并推送一步到位，不用再单独 push）

# ② 顺手推个 latest
docker tag harbor.xxx.edu.cn/myteam/next-app:v1.0.1 harbor.xxx.edu.cn/myteam/next-app:latest
docker push harbor.xxx.edu.cn/myteam/next-app:latest

服务器：拉取 → 换版 → 重启

# ③ 登录仓库（凭证已存则跳过）并拉取新镜像
docker login harbor.xxx.edu.cn
docker pull harbor.xxx.edu.cn/myteam/next-app:v1.0.1
docker images      # 确认新镜像已在列表里

# ④ 停止并删除旧容器（数据在卷里，不会丢！）
docker ps          # 查看正在运行的容器
docker stop app-web
docker rm app-web

# ⑤ 起新容器（run.sh 里版本号已改成 v1.0.1）
./run.sh
# 或 compose 方式（yml 里 image 改成 v1.0.1 后）：
# docker compose pull && docker compose up -d

# ⑥ 看日志确认启动成功 + 迁移执行
docker logs -f app-web

# ⑦ 清理旧镜像（磁盘不够时）
docker rmi harbor.xxx.edu.cn/myteam/next-app:v1.0.0

出问题回滚（30 秒恢复）

# 版本号回退 → 重复 ④⑤ 即可，数据卷不动，数据不受影响
docker stop app-web && docker rm app-web
# run.sh 里版本号改回 v1.0.0
./run.sh

# 注意：若新版执行过"新增字段"的迁移，回滚代码可能遇到旧代码不认识新字段——
# Prisma 迁移原则上只加不减，一般兼容；不确定就先用 pg_dump 备份再回滚
💡 发版口诀
本地 build 推仓库，服务器 pull 停旧删旧起 run；日志确认迁移跑，latest 打底版本号回滚用。

10 常见报错速查表

报错信息（关键词） 原因 解决方法
ECONNREFUSED 127.0.0.1:5432 DATABASE_URL 写了 localhost 容器内改用服务名/容器名：@db:5432（第 1 章预告的头号坑）
exec format error M1/M2 Mac 或默认构建出 arm64 镜像，服务器是 amd64 构建加 --platform linux/amd64
@prisma/client did not initialize yet standalone 镜像没带 Prisma 客户端 Dockerfile 里 COPY node_modules/.prisma 和 @prisma（第 3 章已包含）
Query engine binary not found / openssl alpine 缺 openssl RUN apk add --no-cache openssl，或换 Debian 基础镜像
app 启动报数据库连不上，几秒后自愈 Postgres 还在初始化，app 抢跑了 compose 加 healthcheck + depends_on: condition: service_healthy
P1001: Can't reach database server 网络不对 / 容器名写错 / db 没起 docker compose ps 看 db 状态；确认两个容器在同一 network
页面能开但接口 500 DATABASE_URL 未注入 / 迁移没执行 docker exec -it app-web env | grep DATABASE 查变量；手动跑 migrate deploy
port is already allocated 80 被占用（Nginx / 其他容器） -p 8080:3000 换端口，或停掉占用者；服务器已有 Nginx 就反代到 3000
容器一直 Restarting 启动命令失败反复被拉起 docker logs app-web 看崩溃原因，九成是迁移失败或连不上库
浏览器访问不了，容器内 curl 却通 监听 127.0.0.1 或防火墙拦截 确认 ENV HOSTNAME="0.0.0.0"；安全组/防火墙放行端口
buildx build 完本地没有镜像 buildx 默认不加载到本地列表 本地使用加 --load；直接推仓库加 --push
docker login 报 unauthorized 密码错 / 无该仓库权限 找管理员确认账号和项目组权限（Harbor 按项目授权）
构建巨慢 / 每次全量重装依赖 缓存失效 检查是否先 COPY package.json 再装依赖；.dockerignore 是否排除了 node_modules
bcrypt / sharp 报模块错误 原生模块与镜像系统不匹配 基础镜像统一（都用 node:20-alpine）；或 npm rebuild 对应包
发版后数据没了 没挂数据卷 / 用了 migrate dev 确认 volumes: pgdata 存在；生产只用 migrate deploy
💡 排障三板斧
① docker compose ps 看状态 → ② docker logs -f 容器名 看报错 → ③ docker exec -it 容器名 env / psql 进容器验证环境和数据库。三步之内，90% 的部署问题能定位。

  7. docker restart app-web 后再刷新页面 —— 证明重启自愈正常

口诀总结

💡 十句口诀带走全部
① standalone 先开启，镜像瘦身十倍起；
② 多阶段构建分三步，deps 打底缓存住；
③ alpine 记得装 openssl，Prisma 少它起不来；
④ standalone 不带 Prisma，两个目录要手动拷；
⑤ 容器里 localhost 是自己，连库要用服务名；
⑥ 数据卷不挂，发版数据全丢光；
⑦ healthcheck 门前站，app 不跟 db 抢跑；
⑧ 跨平台构建加 platform，arm 镜像 amd 跑不动；
⑨ 生产只用 migrate deploy，dev 会清库要牢记；
⑩ 发版四连：push、pull、stop+rm、run；日志确认才算完。
