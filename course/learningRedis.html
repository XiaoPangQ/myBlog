Redis 实战指南

从零开始掌握 Redis：安装连接、五大数据类型、Python 实战、缓存三大问题、 持久化与高可用、日常运维，每一步都附常见报错与解决方法， 跟着做完你就能把 Redis 真正用进项目里。

12 个章节 30+ 常见问题 含 Python 实战代码 以 Redis 7.x 为准

01 Redis 是什么：为什么快

一句话定义

Redis 是一个把数据存在内存里的 key-value 数据库。 传统数据库（MySQL）的数据放在硬盘上，Redis 的数据放在内存里—— 而内存的读写速度比硬盘快几个数量级，这就是 Redis 快的根本原因。

打个比方：MySQL 是仓库（什么都能放，但取一次货要跑一趟仓库）， Redis 是柜台（热销货摆在手边，伸手就拿）。 实际项目里两者配合：MySQL 负责可靠存档，Redis 负责快速响应。

📌 先记住三句话，后面全部围绕它们展开
① 快，是因为数据在内存；② 数据可能丢，所以要持久化（RDB/AOF）； ③ 命令执行是单线程，所以并发安全、不用加锁，但也绝不能跑耗时命令。

为什么快：四个原因

原因 说明
纯内存操作 读写不碰硬盘，内存随机访问约 100ns 级，硬盘毫秒级
单线程执行命令 没有线程切换开销、没有锁竞争，一条命令执行时不会被别的命令插队
IO 多路复用 一个线程用 epoll 同时监听成千上万个连接，哪个有请求处理哪个
高效数据结构 SDS 字符串、跳表、压缩列表、哈希表，每种类型都是为场景专门优化过的

常见疑问：「单线程不是慢吗？」——命令执行单线程 ≠ 只有一个线程。 Redis 6.0 之后网络 IO 已经多线程化，但执行命令的核心仍是单线程。 这反而成了优点：天然原子性（INCR 并发加绝不会出错），也没有锁的开销。 代价是：一条慢命令会卡住所有人——这是后面所有「危险命令」警告的根源。

能干什么：八大应用场景

场景 用到的类型 / 能力 举例
缓存（最常见） String + TTL 商品详情、热点文章放缓存，MySQL 只做兜底
Session 共享 String + EXPIRE 多台 Web 服务器共享登录态
排行榜 ZSet 游戏积分榜、销量 Top10、热搜
计数器 / 限流 INCR 原子自增 文章阅读量、接口调用次数限制
消息队列 List / Stream 异步任务、削峰填谷
分布式锁 SET NX EX 多台服务器抢同一个任务时避免重复执行
去重 / 交集 Set 抽奖去重、共同好友、今日已签到用户
签到 / UV 统计 BitMap / HyperLogLog 一年签到只占 365 bit；亿级 UV 估算只占 12KB

什么时候不该用 Redis

需求 为什么不适合 该用什么
数据量远大于内存 装不下就得淘汰，频繁穿透回源反而更慢 MySQL + 合理索引
强事务（转账、扣款） Redis 事务不支持回滚 MySQL 事务
复杂关联查询 没有 join，只能按 key 取 关系型数据库
存大文件 / 图片 内存贵，大 value 拖垮所有请求 对象存储（OSS/COS）+ Redis 存地址
💡 版本说明
本指南以 Redis 7.x 为准，所有命令在 6.x / 5.x 上同样可用（个别新特性会标注）。 查看自己版本的命令：redis-cli INFO server 里的 redis_version 字段。

02 安装与第一次连接

三条安装路线，先选一条

路线 适合 特点
Ubuntu apt 安装 云服务器 / 虚拟机长期使用 最简单，systemd 托管，本指南主线
Docker 安装 本地开发、快速试验 一条命令起一个干净实例，随时销毁重建
Windows 只有 Windows 的本机学习 官方不出 Windows 版，用 WSL2 或 Docker Desktop

路线一：Ubuntu apt 安装（推荐）

# 1. 安装（Ubuntu 20.04 / 22.04 / 24.04 通用）
$ sudo apt update && sudo apt install redis-server -y

# 2. 查看服务状态（看到 active (running) 即成功）
$ sudo systemctl status redis-server

# 3. 设为开机自启（apt 安装通常已自动设置）
$ sudo systemctl enable redis-server

# 4. 验证：能收到 PONG 就是活的
$ redis-cli ping
PONG

路线二：Docker 安装

学过 Docker 的话这是最快的方式（参考之前的 Docker 教程），30 秒得到一个带密码、数据可持久化的实例： 

# -d 后台运行；--restart always 宿主机重启后自动拉起
# -v 把数据挂到数据卷，容器删了数据还在；--requirepass 设置密码
$ docker run -d --name redis --restart always -p 6379:6379 -v redis-data:/data redis:7 --requirepass "你的密码"

# 进入容器里的 redis-cli（-a 带密码；--no-auth-warning 关掉密码明文提示）
$ docker exec -it redis redis-cli -a 你的密码 --no-auth-warning
127.0.0.1:6379> ping
PONG

第一次连接：redis-cli 交互

$ redis-cli              # 直接进入交互模式
127.0.0.1:6379> ping          # 测试连通性
PONG
127.0.0.1:6379> set hello:redis "我跑起来了!"
OK
127.0.0.1:6379> get hello:redis
"我跑起来了!"
127.0.0.1:6379> exit          # 或 Ctrl+D 退出

对外可用前：安全配置（必做）

apt 安装后 Redis 默认只监听 127.0.0.1，本机访问没问题；但要给别的机器（比如你的应用服务器）用，改配置前必须先做好安全： 

$ sudo vim /etc/redis/redis.conf

# ---- 关键四项 ----
bind 0.0.0.0              # 允许外部连接（改之前先确认下面两项已配好！）
requirepass 你的强密码      # 必须设密码
protected-mode yes        # 没设密码时拒绝外部访问，保险丝，保持 yes
port 6379                 # 建议改成非默认端口（可选，减少被扫描概率）

# ---- 可选：禁用危险命令 ----
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command KEYS ""

# 改完重启生效
$ sudo systemctl restart redis-server

# 云服务器还要在安全组放行 6379（只对应用服务器 IP 放行，不要 0.0.0.0/0）
⚠️ 红线：Redis 裸奔公网 = 被挖矿
无密码 + bind 0.0.0.0 + 安全组全开的 Redis，平均几分钟内就会被扫描工具攻陷 （写 crontab 拉挖矿木马是经典套路）。上公网前自查三件事： ① 设了 requirepass；② 安全组只放行应用服务器 IP；③ 能不开公网就只走内网。

本章常见问题

现象 原因 解决方法
Could not connect to Redis at 127.0.0.1:6379: Connection refused 服务没启动 / 端口不对 systemctl status redis-server 看状态；Docker 方式用 docker ps 查
远程连不上，本机能连 bind 只监听 127.0.0.1 / 防火墙 / 安全组没放行 依次查三层：redis.conf 的 bind → 服务器防火墙 ufw → 云厂商安全组
(error) NOAUTH Authentication required 设了密码但连接时没带 redis-cli -a 密码 或进入后 AUTH 密码
(error) WRONGPASS 密码输错 / 配置与运行中不一致 核对 redis.conf 的 requirepass；改过配置要 restart
Windows 下没有 redis 命令 官方不出 Windows 版 用 WSL2（wsl --install）或 Docker Desktop，里面照常 apt 安装
Docker 里 -a 连接报警告 密码出现在命令行会有提示 加 --no-auth-warning，或进入后 AUTH

03 通用命令速览

不管值是什么类型，这些命令对所有 key 都适用，先过一遍混个脸熟：

命令 作用 示例 备注
EXISTS key 是否存在 EXISTS user:1 返回 1 存在 / 0 不存在
TYPE 查看值的类型 TYPE user:1 返回 string / hash / list / set / zset
DEL 删除 key（同步阻塞） DEL user:1 删大 key 会卡，大 key 用 UNLINK
UNLINK 异步删除 UNLINK big:key 后台慢慢回收内存，不卡主线程
EXPIRE 给 key 设过期秒数 EXPIRE user:1 3600 到期自动消失（缓存必备）
TTL 查看剩余存活时间 TTL user:1 见下方返回值表
PERSIST 去掉过期时间（永生） PERSIST user:1 —
RENAME 改名 RENAME old new new 已存在会被覆盖
DBSIZE 当前库 key 总数 DBSIZE —
SCAN 游标分批遍历 key SCAN 0 MATCH user:* COUNT 100 生产唯一推荐的遍历方式
KEYS 按模式列全部 key KEYS user:* 生产禁用，见下方警告
FLUSHDB / FLUSHALL 清空当前库 / 全部库 — 核弹按钮，练习环境再按

TTL 返回值速记

返回值 含义
-2 key 不存在（可能过期了，可能从没有过）
-1 存在，但永不过期
正整数 还剩多少秒到期
⚠️ 为什么生产禁用 KEYS *
Redis 执行命令是单线程的。KEYS * 要一次遍历所有 key， 百万级 key 会卡住 Redis 几秒——这几秒里所有业务请求全部排队，等于全站卡死。 替代方案是 SCAN：像翻书一样一批一批找，每批之间可以处理别的请求，不卡。 
# SCAN 用法：返回 [游标, 一批 key]，游标变回 0 表示遍历结束
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 100
1) "42"                  # 下一批的游标
2) 1) "user:1"
   2) "user:2"
127.0.0.1:6379> SCAN 42 MATCH user:* COUNT 100   # 拿上次的游标继续
1) "0"                  # 游标为 0：遍历完了
2) 1) "user:99"
💡 一个冷知识：TTL 到 0 的瞬间，key 会立刻消失吗？
不一定。过期删除用的是惰性删除 + 定期抽样：访问到过期 key 时顺手删掉，后台每 100ms 抽样主动删。所以个别 key 可能「过期了还占着内存」一小会儿，但对你来说逻辑上等价于不存在（GET 返回 nil）。

04 五大数据类型实战

这是 Redis 的核心。先给一张总表建立全局认知，再逐个实战：

先看总表：什么场景用什么类型

类型 一句话理解 典型场景
String 一个 key 对一个值（字符串 / 数字 / JSON） 缓存、计数器、分布式锁
Hash 一个 key 对一张小表（字段-值），像 Python 字典 购物车、用户资料（可单独改一个字段）
List 双端队列，两头进出有序可重复 消息队列、最新列表
Set 无序自动去重的集合，能算交并差 抽奖、共同好友、去重
ZSet 带分数（score）的 Set，自动按分数排序 排行榜、延迟队列
💡 选型口诀
单值用 String，对象用 Hash；排队用 List，去重用 Set，排名用 ZSet。

4.1 String：最常用的一个

# 基本读写
127.0.0.1:6379> set user:name "zinx"
127.0.0.1:6379> get user:name
"zinx"

# 写入同时设置过期时间（缓存标配写法，3600 秒）
127.0.0.1:6379> set goods:1001 '{"name":"键盘","price":199}' EX 3600

# 不存在才写入（SETNX 语义，分布式锁的核心）
127.0.0.1:6379> set lock:order "abc" NX EX 10
OK   # 第二次执行返回 (nil)，因为已经存在

# 计数器：INCR 原子自增，并发调用也绝不丢数
127.0.0.1:6379> set pv:article:1 0
127.0.0.1:6379> incr pv:article:1
(integer) 1
127.0.0.1:6379> incrby pv:article:1 100
(integer) 101

# 其他常用：批量读 / 追加 / 长度
127.0.0.1:6379> mget user:name pv:article:1    # 一次读多个 key，省往返
127.0.0.1:6379> append user:name "_dev"
127.0.0.1:6379> strlen user:name

为什么 INCR 并发安全？ 因为命令是单线程排队执行的， 10 个请求同时 INCR，就是在队列里排成 10 个加 1，一个都不会丢—— 这就是「天然原子性」，不需要任何锁。

4.2 Hash：把对象按字段存

存用户信息，String 只能把整个 JSON 塞进去（改一个字段要读出→改→写回）； Hash 可以单独读写某个字段： 

# 存对象：一个 key（user:1）下挂多个字段
127.0.0.1:6379> hset user:1 name "zinx" city "成都" vip 1
(integer) 3

# 读单个字段 / 全部字段
127.0.0.1:6379> hget user:1 name
"zinx"
127.0.0.1:6379> hgetall user:1
1) "name"
2) "zinx"
3) "city"
4) "成都"
5) "vip"
6) "1"

# 只改一个字段，不用动其他数据（购物车加一件商品就是这个）
127.0.0.1:6379> hincrby cart:user:1 goods:1001 1

# 判断字段是否存在 / 删除字段
127.0.0.1:6379> hexists user:1 vip
127.0.0.1:6379> hdel user:1 vip
对比项 String 存 JSON Hash 按字段存
改一个字段 GET 整个 JSON → 改 → SET 回去 HSET 一个字段完事
读整个对象 一次 GET HGETALL（字段特别多时慢）
字段数 无限制 建议不超过几百个
适合 整读整写的小对象缓存 常改局部字段的活跃对象

4.3 List：双端队列

# 两头都能进、都能出
127.0.0.1:6379> lpush mq:tasks "任务A" "任务B"   # 从左塞（后塞的在左边）
127.0.0.1:6379> rpush mq:tasks "任务C"            # 从右塞
127.0.0.1:6379> lrange mq:tasks 0 -1              # 看全部（下标 0 到 -1）
1) "任务B"
2) "任务A"
3) "任务C"

# 经典队列模式：LPUSH 进 + BRPOP 出（B=阻塞：队列空就等着，不空转耗 CPU）
127.0.0.1:6379> brpop mq:tasks 5   # 阻塞最多 5 秒等新任务，超时返回 nil
1) "mq:tasks"
2) "任务C"

# 最新列表：只取前 N 条
127.0.0.1:6379> lrange latest:news 0 9    # 最新 10 条
127.0.0.1:6379> llen latest:news          # 长度

4.4 Set：自动去重的袋子

# 添加自动去重
127.0.0.1:6379> sadd lottery:day1 "user:1" "user:2" "user:1"
(integer) 2      # 第三个重复，只加进去 2 个

127.0.0.1:6379> sismember lottery:day1 "user:1"   # 是否已存在（签到去重就靠它）
(integer) 1

# 随机弹出（抽奖）
127.0.0.1:6379> spop lottery:day1 1

# 交集：共同好友 / 共同关注
127.0.0.1:6379> sinter follow:A follow:B
# 并集 / 差集
127.0.0.1:6379> sunion follow:A follow:B
127.0.0.1:6379> sdiff follow:A follow:B   # A 关注了而 B 没关注的

4.5 ZSet：天生排行榜

# 添加成员+分数
127.0.0.1:6379> zadd rank:score 100 "player:1" 250 "player:2" 180 "player:3"

# 按分数从低到高取（ZRANGE）
127.0.0.1:6379> zrange rank:score 0 -1 WITHSCORES
1) "player:1"
2) "100"
3) "player:3"
4) "180"
5) "player:2"
6) "250"

# Top10 排行榜：从高到低取前 10（游戏/销量榜全是这一行）
127.0.0.1:6379> zrevrange rank:score 0 9 WITHSCORES

# 加分（赢了 +50）
127.0.0.1:6379> zincrby rank:score 50 "player:1"

# 我的排名（从 0 开始数）/ 我的分数
127.0.0.1:6379> zrevrank rank:score "player:2"
127.0.0.1:6379> zscore rank:score "player:2"

# 按分数范围取：100~200 分之间（延迟队列取"到期任务"就靠它）
127.0.0.1:6379> zrangebyscore rank:score 100 200

4.6 附加了解：三个特殊类型

类型 绝活 典型用法
BitMap 一个 bit 存一个布尔，极省空间 签到：SETBIT sign:uid:8 26 1（8 月 26 日签到），BITCOUNT 统计签到天数
HyperLogLog 固定约 12KB 估算基数（误差 0.81%） UV 统计：PFADD uv:2026-08-31 uid1 uid2 → PFCOUNT
Stream 真正的消息队列（消费组 + ACK 确认） 要求消息不丢的消费场景；简单场景用 List 就够

本章常见问题

现象 原因 解决方法
(error) WRONGTYPE Operation against a key holding the wrong kind of value 用错命令：对 String 用了 HGET 等 先 TYPE key 看类型，换对应命令；或换一个 key 名
INCR 报 (error) ERR value is not an integer or out of range value 是非数字字符串 INCR 只能用于纯数字的 String
SET 中文后 GET 显示乱码字节 redis-cli 默认按字节显示 启动加 --raw 参数
HGETALL / LRANGE 0 -1 后界面卡住 集合元素太多，一次拉爆了 用 HSCAN / 分页 LRANGE key 0 99；正式环境见第 10 章 bigkey 治理

05 Python + Redis 应用实战

安装与第一次连接

$ pip install redis    # redis-py 5.x，pip 里的 redis 包就是官方库
import redis

r = redis.Redis(
    host="127.0.0.1",
    port=6379,
    password="你的密码",
    db=0,
    decode_responses=True,   # 重要！不加返回的是 bytes，加了对中文直接友好
)

print(r.ping())           # True 即连接成功
r.set("py:hello", "你好 Redis", ex=60)
print(r.get("py:hello"))   # 你好 Redis
⚠️ 最常见的坑：忘记 decode_responses
不加这个参数，get 返回的是 b'\xe4\xbd\xa0\xe5\xa5\xbd' 这样的 bytes， 打印、比较、json.loads 全出错。两种解法：连接时加 decode_responses=True（推荐）， 或每次手动 .decode()。

生产写法：用连接池

每次操作都新建 TCP 连接太浪费。连接池让连接复用——Web 框架（Flask/FastAPI/Django）里 全局建一个池，所有请求共用： 

import redis

# 全局只建一次（比如放在 config.py / app 启动时）
pool = redis.ConnectionPool(
    host="127.0.0.1", port=6379, password="你的密码",
    max_connections=50, decode_responses=True,
    socket_timeout=3, socket_connect_timeout=3,   # 网络抖动时不至于把请求拖死
)
r = redis.Redis(connection_pool=pool)

# 另一种等价写法：URL 方式，配置文件里更整洁
r = redis.Redis.from_url("redis://:你的密码@127.0.0.1:6379/0",
                          decode_responses=True)

五大数据类型的 Python 写法

# ---- String ----
r.set("name", "zinx", ex=3600)       # ex=过期秒数
r.get("name")
r.incr("counter")                      # 自增
r.set("lock:job", "1", nx=True, ex=10)    # 不存在才写

# ---- Hash ----
r.hset("user:1", mapping={"name": "zinx", "city": "成都"})
r.hget("user:1", "name")
r.hgetall("user:1")                      # {'name': 'zinx', 'city': '成都'}
r.hincrby("cart:1", "goods:1001", 1)    # 购物车 +1

# ---- List ----

# ---- Set ----

💡 记忆技巧
redis-py 的方法名就是 Redis 命令的小写：命令 HGETALL → 方法 hgetall()，命令 ZREVRANGE → zrevrange()。 会敲命令就会写 Python。

六个高频实战模式

模式一：旁路缓存（最核心，务必掌握）

读：先查缓存 → 没有再查数据库 → 查到回填缓存。写：先更新数据库，再删除缓存： 

import json

def get_user(user_id):
    cache_key = f"user:{user_id}"
    # ① 先查缓存
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)           # 命中，直接返回（快）
    # ② 没命中，查数据库（慢）
    user = db.query("SELECT * FROM users WHERE id=%s", user_id)
    # ③ 回填缓存，1 小时过期
    r.set(cache_key, json.dumps(user), ex=3600)
    return user

def update_user(user_id, **fields):
    db.execute("UPDATE users SET ... WHERE id=%s", user_id)   # 先更新库
    r.delete(f"user:{user_id}")   # 再删缓存（下次读自动回填新值）
📌 为什么是「删缓存」而不是「改缓存」？
改缓存要算出新值再写入，并发两个写请求容易把旧值写回去（脏数据）； 删除是无脑幂等操作——下次读的时候自然会加载最新数据。这套「Cache Aside」是业界默认答案。

模式二：计数器 / 接口限流

# 文章阅读量：一条命令搞定，天然并发安全
r.incr(f"pv:article:{article_id}")

# 接口限流：每个 IP 每分钟最多 60 次
def allow_request(ip):
    key = f"rate:{ip}"
    current = r.incr(key)
    if current == 1:
        r.expire(key, 60)        # 第一次访问时设置 60 秒窗口
    return current <= 60

模式三：排行榜

# 玩家得分变动
r.zincrby("rank:score", 25, "player:1001")

# 拉取 Top10（返回 [(成员, 分数), ...]，从高到低）
top10 = r.zrevrange("rank:score", 0, 9, withscores=True)

# 我的全国排名（0 = 第一名）
my_rank = r.zrevrank("rank:score", "player:1001")

模式四：分布式锁（面试高频）

import uuid, time

# 加锁：NX 保证只有一个客户端能成功；EX 是锁的自动过期（防止持有者崩了锁永远不释放）
def acquire_lock(name, timeout=10):
    lock_id = str(uuid.uuid4())       # 每个持锁者一个唯一 ID
    deadline = time.time() + timeout
    while time.time() < deadline:      # 没抢到就自旋重试
        if r.set(f"lock:{name}", lock_id, nx=True, ex=10):
            return lock_id
        time.sleep(0.05)
    return None                       # 超时没抢到

# 解锁：必须用 Lua 校验"锁还是我的"再删，防止误删别人的锁
RELEASE_LUA = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
"""

def release_lock(name, lock_id):
    return r.eval(RELEASE_LUA, 1, f"lock:{name}", lock_id)

# 使用
lock_id = acquire_lock("sync_job")
if lock_id:
    try:
        do_sync_job()               # 三台服务器同时跑，只有一台真正执行
    finally:
        release_lock("sync_job", lock_id)
⚠️ 为什么解锁要用 Lua？
「先 GET 判断再 DEL」是两步操作，中间可能锁恰好过期被别人抢走——DEL 删掉的就是别人的锁。 Lua 脚本在 Redis 里原子执行（判断+删除一气呵成），不会被人插队。 生产更完善的方案直接用现成库 pip install redlock。

模式五：简单异步任务队列

# 生产者（Web 接口里）：发邮件、生成报表等耗时操作扔进队列
r.lpush("mq:email", json.dumps({"to": "a@x.com", "subject": "注册成功"}))

# 消费者（独立进程跑的 worker）
while True:
    item = r.brpop("mq:email", timeout=0)    # 阻塞等任务，不空转
    if item:
        _, data = item
        send_email(json.loads(data))

模式六：登录 Session / 验证码

# 登录成功：生成 session，30 分钟有效（setex = set + expire 合一）
session_id = str(uuid.uuid4())
r.setex(f"sess:{session_id}", 1800, json.dumps({"user_id": 42}))

# 每次请求校验：中间件里做
def get_session(session_id):
    data = r.get(f"sess:{session_id}")
    return json.loads(data) if data else None      # None = 未登录/已过期

# 验证码：5 分钟有效，天然倒计时
r.setex(f"code:{phone}", 300, "836291")

06 缓存三大问题：穿透 / 击穿 / 雪崩

只要把 Redis 当缓存用，这三个问题迟早会撞上，也是面试必问。先看正常流程长什么样： 

 正常的缓存流程（一切美好）
 ──────────────────────────────
 请求 ──► ① 查 Redis ──命中──► 直接返回（快）
              │
             未命中
              ▼
         ② 查 MySQL ──► ③ 结果写回 Redis（带回 TTL）──► 返回

6.1 缓存穿透：查「根本不存在」的数据

现象：请求的 key 在缓存和数据库里都不存在（比如恶意攻击者拿 id=-1、id=99999999 疯狂请求）。缓存永远不命中， 每个请求都直奔 MySQL——缓存形同虚设。 

 穿透：恶意请求打在"不存在的数据"上
 ──────────────────────────────
 恶意请求 ──► Redis 没有 ──► MySQL 也没有 ──► 无法回填缓存
    ▲           （永远不会命中）              │
    └──────── 下一个同样的请求，还是全落到 MySQL ─┘

三种解法（组合使用）：

  1. 缓存空值：数据库也查不到时，往 Redis 写一个空标记（短 TTL）， 下次同样的请求就被挡在缓存层
  2. 入口校验：id <= 0、非法格式直接拒绝，根本不往下走
  3. 布隆过滤器：启动时把所有合法 id 装进过滤器，请求先问一句 「这个 id 可能存在吗」，不存在直接返回（适合 id 集合稳定的场景） 
def get_goods(goods_id):
    if goods_id <= 0:                         # 解法② 入口校验
        return None
    key = f"goods:{goods_id}"
    cached = r.get(key)
    if cached == "__NULL__":                    # 解法① 空值缓存命中
        return None
    if cached:
        return json.loads(cached)
    goods = db.query_goods(goods_id)
    if goods is None:
        # 库里也没有：写空标记，60 秒后过期
        # （TTL 要短，防止新商品上架后一直返回"不存在"）
        r.set(key, "__NULL__", ex=60)
        return None
    r.set(key, json.dumps(goods), ex=3600)
    return goods

6.2 缓存击穿：热点 key 过期的那一瞬间

现象：某个超级热点的 key 过期的瞬间， 大量并发同时未命中，全部涌向数据库重建缓存，数据库瞬间被打爆。 典型场景：秒杀商品详情、热搜词条。 

 击穿：热 key 过期瞬间，重建请求挤破门
 ──────────────────────────────
       ┌── 请求1 ──┐
       ├── 请求2 ──┤    热点 key 过期
       ├── 请求3 ──┼──► 全部同时未命中 ──► 全部去查 MySQL（爆）
       └── 请求N ──┘

两种主流解法：

  1. 互斥锁重建：只放一个请求去查库重建，其他请求短暂等待后重读缓存。 保证一致，但其他请求要等一下
  2. 逻辑过期：key 不设物理 TTL，把过期时间写进 value 里； 发现逻辑过期时先返回旧数据，同时异步开一个线程去重建。 绝不阻塞用户，但短时间内返回的是旧数据 
# 解法①：互斥锁重建（简单可靠，中小项目首选）
import time

def get_hot_data(key):
    cached = r.get(key)
    if cached:
        return json.loads(cached)

    lock_key = f"rebuild:{key}"
    # 抢到锁的幸运儿去查库
    if r.set(lock_key, "1", nx=True, ex=10):
        try:
            data = db.query_hot(key)
            r.set(key, json.dumps(data), ex=3600)
            return data
        finally:
            r.delete(lock_key)

    # 没抢到锁的：小睡片刻后重读缓存（重建大概率已完成）
    time.sleep(0.1)
    return get_hot_data(key)

6.3 缓存雪崩：一大片同时倒下

两种形态：

  • 大面积同时过期：批量导入数据时给了相同的 TTL，到期那一刻洪峰直冲数据库
  • Redis 整个挂了：所有请求全部落到数据库，连锁雪崩

四件武器：

武器 针对形态 做法
TTL 加随机值 同时过期 ex = 3600 + random.randint(0, 600)，把过期时间打散
高可用 Redis 挂掉 主从 + 哨兵（第 9 章），挂了自动切
多级缓存 两者皆可 本地缓存（进程内 dict）→ Redis → DB，层层兜底
限流降级 最后一道墙 DB 前加限流（每秒最多 N 个回源请求），超出的返回默认值/排队

三兄弟对照表（面试就答这张）

问题 本质区别 一句话解法
穿透 查不存在的数据，缓存永远无法命中 缓存空值 + 入口校验 + 布隆过滤器
击穿 单个热点 key 过期瞬间被击穿 互斥锁重建 / 逻辑过期
雪崩 大面积同时过期或 Redis 整体宕机 TTL 加随机 + 高可用 + 多级缓存 + 限流
💡 口诀：三个问题一句话记住
穿透是「查不到」：空值缓存来兜底；
击穿是「热 key 掉」：互斥重建别拥挤；
雪崩是「一起倒」：过期加随机、高可用不能少。

07 过期与内存淘汰

内存满了会怎样：先懂 maxmemory

Redis 把数据全放内存，内存不是无限的。maxmemory 设定可用上限， 超过之后怎么办？——由淘汰策略（maxmemory-policy）决定。 两者都可以不重启直接改： 

# 查看当前配置
127.0.0.1:6379> CONFIG GET maxmemory
127.0.0.1:6379> CONFIG GET maxmemory-policy

# 运行时立即生效（重启后失效；要长期生效写进 redis.conf）
127.0.0.1:6379> CONFIG SET maxmemory 512mb
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lru

# 顺便看内存占用情况
127.0.0.1:6379> INFO memory     # 重点看 used_memory_human

八种淘汰策略一览

策略 淘汰谁 适合
noeviction（默认） 谁也不淘汰，直接报错拒绝写入 数据不能丢的场景；缓存场景不建议
allkeys-lru 所有 key 里，淘汰最久没用的 纯缓存场景首选
allkeys-lfu 所有 key 里，淘汰访问次数最少的 缓存且区分「偶尔访问一次」和「高频访问」
allkeys-random 所有 key 里，随机淘汰 极少用
volatile-lru 设了 TTL 的 key 里，淘汰最久没用的 缓存+持久数据混用一个实例
volatile-lfu 设了 TTL 的 key 里，淘汰访问最少的 同上
volatile-random 设了 TTL 的 key 里，随机淘汰 极少用
volatile-ttl 设了 TTL 的 key 里，淘汰剩余存活时间最短的 让「快过期的先走」
💡 选型速记
LRU 看「多久没访问」，LFU 看「访问频率高不高」。 纯缓存选 allkeys-lru / allkeys-lfu；混着存数据选 volatile 系列； 一点都不能丢选 noeviction（但要盯内存，写满会报错）。 生产上推荐「缓存和存储分实例部署」，缓存实例用 allkeys-lru，谁也不用纠结。
⚠️ 一个高频线上事故
某天应用突然大量报错 (error) OOM command not allowed when used memory > 'maxmemory' ——就是默认的 noeviction 策略 + 内存写满。缓存场景的解法： CONFIG SET maxmemory-policy allkeys-lru 立即恢复写入， 再考虑加内存或清理大 key。

过期 key 是怎么被删掉的

上一章说过「惰性删除 + 定期抽样」，这里补一个推论：

  • 大量 key 设了相同的 TTL，到期后内存不一定立刻回落——定期抽样删不过来时， 可能要等访问触发惰性删除。这也是雪崩问题里「TTL 加随机值」的另一个理由
  • 想立刻回收内存的写法：删 key 用 UNLINK（异步），比 DEL 友好
  • INFO memory 里的 expired_keys 可以看到累计删除的过期 key 数量

08 持久化：RDB 与 AOF

内存一断电就清空。Redis 提供两套持久化机制把数据落到硬盘， 重启后能恢复：RDB（快照）和 AOF（命令日志）。

RDB：定时快照

相当于给内存拍照片：某一时刻的全部数据一次性写进 dump.rdb 文件。 触发方式有自动（配置规则）和手动： 

# redis.conf 中的自动触发规则（默认）
save 3600 1      # 3600 秒内至少 1 次修改 → 触发快照
save 300 100     # 300 秒内至少 100 次修改 → 触发
save 60 10000    # 60 秒内至少 10000 次修改 → 触发

# 手动触发
127.0.0.1:6379> BGSAVE    # 后台保存（fork 子进程去干，不阻塞主线程，推荐）
127.0.0.1:6379> SAVE      # 前台保存（阻塞所有人，只该在维护窗口用）
127.0.0.1:6379> LASTSAVE  # 上次成功保存的时间戳

优点：文件紧凑、恢复飞快（直接把照片加载进内存）。 缺点：两次快照之间的数据会丢——比如每 5 分钟一次快照，最坏丢最近 5 分钟。

AOF：命令日志

相当于记账：每条写命令都追加记录到 appendonly.aof， 重启时把日志从头到尾重放一遍恢复数据。丢多少取决于刷盘策略：

appendfsync 策略 含义 丢数据 性能
always 每条命令都刷盘 最多丢 1 条 最慢，一般不用
everysec（推荐） 每秒刷一次盘 最多丢 1 秒 兼顾性能与安全
no 交给操作系统，攒多了自己刷 不可控 最快

日志会越记越长（「+1 又 -1」这种抵消操作都留着），所以有 AOF 重写： 把当前内存状态用最少的命令重新写一份新日志（自动触发条件 auto-aof-rewrite-percentage 100：日志比上次重写后翻倍就重写）。

怎么选：一张表 + 一个推荐

对比项 RDB AOF
本质 某一时刻的全量照片 全部写命令的日志
文件大小 小 大（重写后可缩小）
恢复速度 快（直接加载） 慢（逐条重放）
数据丢失 最多丢一个快照周期 everysec 最多丢 1 秒
性能影响 fork 瞬间可能卡一下 持续小开销
💡 推荐配置：混合持久化（4.0+，5.0 后默认开启）
aof-use-rdb-preamble yes——AOF 重写时，文件前半段写成 RDB 格式的全量快照， 后半段追加增量命令。恢复快（读快照）+ 丢得少（增量日志），两全其美。 开启方式：redis.conf 里 appendonly yes + aof-use-rdb-preamble yes。

简单决策：纯缓存（丢了能重建）→ 只开 RDB 甚至不开；数据重要 → 开混合持久化。
⚠️ 持久化 ≠ 备份
硬盘坏了 / 误删目录 / 勒索病毒，dump.rdb 和 aof 一起没了。 定期把 RDB 文件 scp / 上传到另一台机器或对象存储，才是真正的备份。

本章常见问题

现象 原因 解决方法
MISCONF Redis is configured to persist RDB snapshots... BGSAVE 失败（磁盘满 / 权限），默认会拒绝写入自保 清磁盘、修权限后 CONFIG SET stop-writes-on-bgsave-error no 临时恢复写入（治标），根治要修磁盘问题
重启后数据丢了 没开持久化 / 丢在快照间隔内 / save 规则太宽松 确认 CONFIG GET save；重要数据开 AOF everysec
BGSAVE 时业务卡一下 fork 子进程复制页表，大内存实例 fork 慢 降低 fork 频率；确认 Linux 关闭大页 echo never > /sys/kernel/mm/transparent_hugepage/enabled
AOF 文件损坏导致起不来 断电写了一半 redis-check-aof --fix appendonly.aof 修复截断部分

09 高可用：主从 / 哨兵 / 集群

单机 Redis 有两个天花板：挂了就全停（可用性）、一台内存装不下（容量）。三代架构逐级解决： 

 单机          主从（读写分离）        哨兵（自动故障转移）      集群（数据分片）
 ┌─────┐      ┌─────────────┐      ┌───────────────────┐   ┌─────────────────┐
 │Redis│      │   Master ◄──┼──写  │ Sentinel1  Sentinel2│   │ Master1 Master2  │
 │     │ ──►  │     │复制    │      │     ▼ 监控投票      │   │ Master3 ...     │
 └─────┘      │  Replica1   │      │ Master ◄─自动选主    │   │ 每个主挂从       │
   挂了全停    │  Replica2   │      │ Replica 升级接替    │   │ key 分 16384 槽  │
              └─────────────┘      └───────────────────┘   └─────────────────┘
              主挂需手动切            挂了自动切               容量/写性能水平扩展

主从复制：一拖 N

# 从库上执行（或写进它的 redis.conf： replicaof 主IP 6379）
127.0.0.1:6380> REPLICAOF 192.168.1.10 6379

# 验证：主库 INFO replication 应看到 connected_slaves: 1
127.0.0.1:6379> INFO replication
role:master
connected_slaves:1
  • 写走主库，读走从库（读写分离），从库默认只读
  • 主库挂了要人工把从库切成主：REPLICAOF NO ONE——哨兵就是干这个的自动化版

哨兵：给主从配个监工

哨兵进程（通常部署奇数个，如 3 个）盯着主库：ping 不通就投票，多数同意就判定下线， 自动挑一个从库升级为新主，通知客户端切换。客户端不再直连 Redis，而是先问哨兵「现在的主库是谁」。 

# sentinel.conf（三个哨兵各一份，指向同一个主库）
sentinel monitor mymaster 192.168.1.10 6379 2   # 2 = 至少 2 个哨兵同意才判定主库下线
sentinel down-after-milliseconds mymaster 5000  # 5 秒无响应视为失联

# 启动哨兵
$ redis-sentinel /etc/redis/sentinel.conf

集群：数据分片，水平扩展

当一台机器的内存装不下（比如 > 25GB）或写入量单机扛不住时上集群： 全部 key 划分成 16384 个槽（slot），按 key 的 CRC16 值 mod 16384 分散到多个主节点。官方建议至少 6 台（3 主 3 从）。 

# 6 个实例的 redis.conf 都开集群模式（port 分别 7001-7006）
cluster-enabled yes
cluster-config-file nodes-7001.conf

# 一条命令组建集群（3 主 3 从自动分配）
$ redis-cli --cluster create 192.168.1.10:7001 192.168.1.10:7002 \
  192.168.1.11:7003 192.168.1.11:7004 192.168.1.12:7005 192.168.1.12:7006 \
  --cluster-replicas 1
⚠️ 集群的代价（不是免费午餐）
① 多 key 操作受限：不在同一 slot 的 key 不能一起 MGET/事务， 要用 {} hash tag 强制同槽（如 user:{1001}:cart 和 user:{1001}:profile）； ② 运维复杂度直线上升。数据量没到瓶颈就别上集群，哨兵足够应付大多数项目。

选型对照

架构 解决什么 复杂度 什么时候用
单机 — ★ 学习、个人项目、缓存丢了无所谓
主从 读扩展 + 数据热备 ★★ 读多写少；体验复制机制
哨兵 主从 + 自动故障转移 ★★★ 大多数生产项目的甜点位
集群 + 容量/写性能水平扩展 ★★★★ 数据量 > 单机内存、写 QPS 极高
💡 口诀
主从备份读写分，哨兵盯着自动切；槽位分片上集群，没到瓶颈别折腾。

10 日常运维与性能排查

INFO：健康检查的第一站

127.0.0.1:6379> INFO memory       # 内存
127.0.0.1:6379> INFO clients       # 连接
127.0.0.1:6379> INFO stats         # 流量统计
127.0.0.1:6379> INFO keyspace     # 各库 key 数量与带 TTL 的比例
字段 看什么 异常信号
used_memory_human 当前内存占用 逼近 maxmemory → 准备淘汰/扩容
connected_clients 当前连接数 持续逼近 maxclients（默认 10000）→ 应用可能在泄漏连接
instantaneous_ops_per_sec 每秒命令数 与业务量对不上 → 被滥用/被攻击
evicted_keys 因内存满被淘汰的 key 累计数 持续增长 → 内存吃紧，缓存命中率在下降
expired_keys 累计过期删除数 正常现象，用于确认 TTL 生效
keyspace 如 db0:keys=100000,expires=80000 expires 占比过低 → 大量 key 没设 TTL，内存会只涨不降

慢查询：谁在拖慢 Redis

# 阈值：记录超过 10ms 的命令（微秒为单位，10000µs = 10ms）
127.0.0.1:6379> CONFIG SET slowlog-log-slower-than 10000

# 查看最近 10 条慢查询
127.0.0.1:6379> SLOWLOG GET 10
1) 1) (integer) 14            # 编号
   2) (integer) 1725091200     # 发生时间戳
   3) (integer) 25000          # 耗时 25000µs = 25ms
   4) 1) "KEYS"                # 元凶命令
      2) "*"

bigkey：藏在暗处的性能杀手

bigkey 不是 key 名长，而是value 特别大（百万元素的集合、几 MB 的字符串）。 危害：读写耗时长、网络传输占带宽、删除时阻塞主线程、集中过期时引发卡顿。 

# 扫描：只采样不阻塞（生产可用）
$ redis-cli --bigkeys -i 0.1        # -i 每次扫描间隔 0.1s，更温柔

# 精确看某个 key 占多少内存
127.0.0.1:6379> MEMORY USAGE big:hash:key
(integer) 6291456        # 字节数

# 找热 key（需 LFU 淘汰策略才有数据）
$ redis-cli --hotkeys

bigkey 治理三板斧：

  1. 拆：大 Hash 按 big:key:{0..99} 拆成 100 个小 Hash；大 List 截断只留需要的部分
  2. 异步删：用 UNLINK 代替 DEL
  3. 压缩：value 先压缩再存（Python zlib / gzip），读时解压

危险命令红线表（贴在工位那种）

命令 危险等级 替代做法
KEYS * 🔴 卡死全站 SCAN 0 MATCH xxx:* COUNT 100
FLUSHALL / FLUSHDB 🔴 清空全部数据 生产用 rename-command 禁用；测试环境才可执行
HGETALL 大key / LRANGE 0 -1 🟠 一次拉爆网络 HSCAN / 分页取
DEL 大key 🟠 主线程卡顿 UNLINK
MONITOR 生产长开 🟠 吞吐降一半 临时排查几秒就关

排查三板斧（总结）

📌 Redis 变慢了怎么查：固定顺序
① INFO memory 看内存是否打满（evicted_keys 在涨？）→ ② SLOWLOG GET 找慢命令（KEYS？大集合操作？）→ ③ --bigkeys 找大 key、--hotkeys 找热 key。 三步下来 90% 的性能问题都能定位。

11 常见报错速查表

实战中最常撞见的报错都在这了，按「看到什么 → 为什么 → 怎么修」组织：

报错 / 现象 原因 解决方法
Could not connect ... Connection refused 服务未启动 / 端口不对 systemctl status redis-server；Docker 用 docker ps；核对端口
远程能 telnet 通但 redis-cli 连不上 bind 限制 / protected-mode redis.conf 改 bind、设密码后 protected-mode 不会拦截外部
(error) NOAUTH 没带密码 redis-cli -a 密码 或 AUTH 密码
(error) WRONGPASS 密码错误 核对 requirepass；注意配置改后要 restart
OOM command not allowed when used memory > 'maxmemory' noeviction 策略 + 内存满 CONFIG SET maxmemory-policy allkeys-lru；长期看加内存/清 bigkey
MISCONF Redis is configured to persist RDB snapshots... 磁盘满/权限导致 BGSAVE 失败 清磁盘修权限；临时 CONFIG SET stop-writes-on-bgsave-error no
(error) WRONGTYPE ... 命令与 key 类型不匹配 TYPE key 确认类型换命令
ERR value is not an integer 对非数字 String 做 INCR 保证 INCR 的 key 只存数字
READONLY You can't write against a read only replica 连的是从库（从库只读） 写操作走主库地址
LOADING Redis is loading the dataset in memory 启动中正在加载持久化文件 等它加载完（数据多会久一点），别急着重启
BUSY Redis is busy running a script Lua 脚本死循环卡住主线程 SCRIPT KILL（还没写入时有效）；写过的只能 SHUTDOWN NOSAVE
get 中文是 \xe4\xbd\xa0... 字节显示模式 redis-cli 加 --raw；Python 加 decode_responses=True
Python ConnectionError: Connection reset by peer 连接被 Redis 断开：超时被踢 / 服务重启 / 网络闪断 redis-py 会自动重连重试；频繁出现查 timeout 配置和网络
主从复制频繁断开重连 网络抖动 / 主库写入压力过大 / repl-backlog 太小 查网络；调大 repl-backlog-size（如 256mb）
Docker 容器里 Redis 时快时慢 宿主机内存不足 / 磁盘 IO 争抢 限制容器内存 --memory；确认持久化文件在 SSD

十句口诀收尾

💡 Redis 十句口诀
① 内存快持久慢，Redis 定位要记牢；
② 单值 String 对象 Hash，排队 List 去重 Set，排名就用 ZSet；
③ KEYS 生产是禁令，遍历请用 SCAN；
④ 大 key 别全量读，分页扫描慢慢来；
⑤ 读走缓存 miss 回源，写完数据库删缓存；
⑥ 穿透空值挡，击穿互斥忙，雪崩过期加随机；
⑦ 淘汰策略先想清，纯缓存 allkeys-lru 最稳；
⑧ RDB 快照恢复快，AOF 日志丢得少，混合持久化两全好；
⑨ 变慢三板斧：INFO、SLOWLOG、bigkeys；
⑩ 密码白名单要配好，公网裸奔是灾难。
